## **4. 브랜치·커밋 규칙**

**main은 항상 돌아가는 상태. 작업은 내 브랜치에서.**

### **브랜치**

| 브랜치 | 용도 | 누가 |
| --- | --- | --- |
| `main` | 항상 돌아가는 상태 | 직접 push 금지 |
| `feat/기능명` | 기능 개발 | 각자 |
| `fix/버그명` | 버그 수정 | 각자 |

main 반영: `feat/fix 브랜치 push → GitHub에서 PR 생성 → 팀장(장범수) 확인 후 main에 merge`

### **커밋 메시지**

형식: `YYMMDD 태그 : 내용` (예: `261027 UPDATE : 내용`)

| 태그 | 언제 | 예시 |
| --- | --- | --- |
| `FEAT` | 새 기능 추가 | `261027 FEAT : 학습 데이터 전처리 추가` |
| `UPDATE` | 기능 개발 중 버그 때문에 수정 (내 feat 브랜치 안에서) | `261027 UPDATE : 학습 중 GPU 메모리 부족 오류 수정` |
| `FIX` | main에 이미 들어간 기능의 버그 수정 (`fix/` 브랜치) | `261027 FIX : 추론 결과 좌표 계산 오류 수정` |
| `DOCS` | README·CLAUDE.md 등 문서만 수정 | `261027 DOCS : 실행 방법 추가` |
| `REFACTOR` | 동작은 그대로, 코드 구조만 정리 | `261027 REFACTOR : 학습·추론 코드 함수 분리` |

### **작업 흐름**

```bash
git switch main
git pull                        # 남의 작업 먼저 받기
git switch -c feat/preprocess   # 내 브랜치 만들기

# ... 작업 ...

git add .
git commit -m "261027 FEAT : 학습 데이터 전처리 추가"
git push -u origin feat/preprocess
```

## **5. 건드리면 안 되는 파일·폴더**

- `.env`, `.key` — 비밀 키 파일. 읽거나 수정하거나 커밋하지 않는다.
- 데이터셋·영상·학습 가중치 등 대용량 파일은 GitHub에 올리지 않는다. Google Drive에서 공유·관리한다.
- [미정: 추가 항목]

## **6. 비밀 키 관리 (가장 중요)**

**키는 `.env`에만. 한 번 올라가면 지워도 남는다.**

- API 키·비밀번호를 코드에 직접 쓰지 않는다. `.env`에 넣고 코드에서는 불러와서만 쓴다.
- `.env`, `.key`는 `.gitignore`에 들어 있다. 커밋하기 전에 비밀 키가 들어가지 않았는지 확인한다.
- 키가 한 번 GitHub에 올라가면 커밋 이력에 남아서 나중에 파일을 지워도 남는다. 올라갔다면 바로 팀에 알리고 키를 새로 발급받는다.

# **Part 2. Claude 작업 원칙**

## **1. 코딩 전에 생각하기**

**가정하지 않는다. 헷갈림을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현하기 전에:

- 가정을 분명히 말한다. 확실하지 않으면 묻는다.
- 해석이 여러 가지면 모두 제시한다. 혼자 조용히 고르지 않는다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반대 의견을 낸다.
- 불분명하면 멈춘다. 무엇이 헷갈리는지 말하고 묻는다.

## **2. 단순함 우선**

**문제를 푸는 최소한의 코드. 추측으로 만든 것은 없다.**

- 요청하지 않은 기능을 넣지 않는다.
- 한 번만 쓰는 코드에 추상화를 만들지 않는다.
- 요청하지 않은 "유연성"이나 "설정 기능"을 넣지 않는다.
- 일어날 수 없는 상황에 대한 예외 처리를 넣지 않는다.
- 200줄로 썼는데 50줄로 될 수 있으면 다시 쓴다.

스스로 묻는다: "시니어 개발자가 보면 너무 복잡하다고 할까?" 그렇다면 단순하게 고친다.

## **3. 필요한 곳만 수정**

**꼭 필요한 곳만 건드린다. 내가 어지른 것만 치운다.**

기존 코드를 고칠 때:

- 주변 코드·주석·서식을 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩터링하지 않는다.
- 내 취향과 달라도 기존 스타일을 따른다.
- 관계없는 죽은 코드를 발견하면 말만 하고 지우지 않는다.

내 수정 때문에 안 쓰이게 된 것이 생기면:

- 내 수정으로 안 쓰이게 된 import·변수·함수는 지운다.
- 원래 있던 죽은 코드는 요청이 없으면 지우지 않는다.

확인 기준: 바뀐 모든 줄이 요청과 직접 연결되어야 한다.

## **4. 목표 기준 실행**

**성공 기준을 정하고, 확인될 때까지 반복한다.**

작업을 확인할 수 있는 목표로 바꾼다:

- "입력 검사 추가" → "잘못된 입력 테스트를 만들고 통과시키기"
- "버그 수정" → "버그를 재현하는 테스트를 만들고 통과시키기"
- "X 리팩터링" → "수정 전후로 테스트가 통과하는지 확인"

테스트가 아직 없으면 직접 실행해서 결과를 확인한다.

여러 단계 작업은 짧은 계획을 먼저 말한다:

```
1. [단계] → 확인: [무엇으로 확인]
2. [단계] → 확인: [무엇으로 확인]
3. [단계] → 확인: [무엇으로 확인]
```

성공 기준이 분명하면 혼자 끝까지 갈 수 있다. "되게 해줘" 같은 약한 기준은 계속 확인을 받아야 한다.
